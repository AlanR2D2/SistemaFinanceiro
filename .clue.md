## Visão Geral

Sistema web de **gestão financeira jurídica** para controle de **Acordos** e **Mandados** judiciais. Permite CRUD completo, dashboard com KPIs e gráficos, gerenciamento de cadastros auxiliares, usuários e configurações pessoais.

### Stack

| Camada         | Tecnologia                                         |
|----------------|-----------------------------------------------------|
| Backend        | **Flask** (Python 3.12) — porta `5001`              |
| Banco de dados | **Supabase** (PostgreSQL gerenciado, SDK Python)     |
| Frontend       | **Jinja2 templates** + TailwindCSS (CDN) + Feather Icons + Chart.js |
| Produção       | **Docker** + **Gunicorn** (3 workers, gthread)       |
| Proxy reverso  | **Caddy** (HTTPS automático)                         |
| Sync de dados  | Scripts Python que leem **Google Sheets** e inserem no Supabase |
| E-mail         | SMTP Gmail (senha de app)                            |

### URL de Produção

`financeiro.n8n-draconsumidor.com.br` (gerenciado pelo Caddy)

## Autenticação e Autorização

### Mecanismo

- **Flask-Login** gerencia sessões.
- Senhas armazenadas com **hash Werkzeug** (pbkdf2/scrypt).
- Migração automática de senhas legadas em texto plano para hash no primeiro login bem-sucedido.
- Classe `User(UserMixin)` carregada por `login` (campo PK de `fin_users`).

### Hierarquias (Permissões)

| Hierarquia   | Permissões                                                    |
|--------------|---------------------------------------------------------------|
| `admin`      | Tudo: CRUD acordos/mandados, cadastros auxiliares, usuários   |
| `financeiro` | CRUD acordos/mandados, cadastros auxiliares                   |
| `gestor`     | CRUD acordos/mandados, cadastros auxiliares                   |
| `user`       | CRUD acordos/mandados, configurações pessoais                 |

- A função `require_admin()` permite acesso a `admin`, `financeiro` e `gestor`.
- No sidebar, links de "Cadastros" e "Usuários" só aparecem para `admin` / `administrador` / `master`.
- Todos os usuários podem alterar nome, e-mail e senha na página de Configurações.

## Regras de Negócio Importantes

### Finalizado (derivação automática)

- O campo `finalizado` (0 ou 1) é **derivado automaticamente** do campo `status`.
- `finalizado = 1` quando `status` começa com `"FINALIZADO"` (case-insensitive).
- Isso é aplicado tanto no CRUD do app.py (função `_derive_finalizado_from_status`) quanto nos scripts de sync (função `_status_is_finalizado` com lista expandida de keywords).
- Os scripts de sync reconhecem mais variações: ENCERRADO, CONCLUÍDO, PAGO, etc.

### Campos numéricos / monetários

- Acordos: `valor_acordo`, `deposito`, `correcao`, `honorarios`, `repasse`, `sucumbencia`, `porcentagem_honorarios`
- Mandados: `deposito`, `correcao`, `honorarios`, `repasse`, `sucumbencia`, `porcentagem_honorarios`
- Função `parse_numeric()` converte formatos BR (`1.234,56`) e US para float.
- Função `clean_payload()` sanitiza o payload antes de inserir/atualizar, removendo campos `None`.

### Datas

- Entrada do frontend: formato brasileiro `dd/mm/aaaa`.
- Armazenamento: ISO `yyyy-mm-dd`.
- Funções: `br_to_iso_date()` e `iso_to_br_date()` fazem a conversão bidirecional.

### Cadastros auxiliares

- Valor em uso em Acordos/Mandados: **não pode ser renomeado nem excluído**.
- Apenas o campo "Ativo" pode ser alterado quando o valor está em uso.
- Cadastros com `cor` e `cor_letra` permitem personalizar a cor de fundo e da letra das linhas na tabela.
- Campo `hierarquia` no cadastro controla prioridade de exibição (1 = prioridade alta, 2 = normal).

### Cores de linhas

- As tabelas de acordos e mandados aplicam cores por status/local/conta.
- Endpoint `/api/row-colors` retorna o mapa `{ status: { NOME: { cor, cor_letra, hierarquia } }, local: {...}, conta: {...} }`.
- O frontend JavaScript aplica essas cores às linhas da tabela (`<tr>` style).

## Sincronização Google Sheets → Supabase

### Planilha

- ID: `1X5onhlmX_V37HvhNxLF-nqkNzFllXOwIjqw6N3uPMH0`
- Abas de mandados: `MANDADOS`, `MANDADOS FINALIZADOS`
- Abas de acordos: `ACORDOS`, `ACORDOS FINALIZADOS`

### Fluxo (sync_mandados.py e sync_acordos.py)

1. Autenticar via Service Account (`credentials.json`) com gspread.
2. Ler as duas abas (ativos + finalizados) da planilha.
3. Normalizar cabeçalhos (acentos, casing) e mapear para nomes de colunas do Supabase.
4. Converter datas (`pd.to_datetime`, dayfirst), valores monetários (`_to_money`), e strings.
5. Derivar `finalizado` (0/1) a partir do campo `status`.
6. Filtrar colunas para manter apenas as permitidas (`ALLOWED_COLUMNS`).
7. **Deletar todos os registros** da tabela destino (`delete_all`).
8. **Inserir em bulk** todos os registros lidos (`bulk_insert`, chunks de 300).

### Observações de sync

- O `delete_all` usa `neq(col, "__never__")` como workaround do PostgREST.
- O `bulk_insert` sanitiza NaN, Inf → None e date → ISO string.
- Os scripts são executados manualmente ou via cron/n8n (não integrados no Flask).

## Frontend (Templates)

### Arquitetura

- `base.html` é o layout base com **sidebar colapsável**, navegação, mobile responsivo.
- Templates de lista (`acordos_ativos.html`, etc.) herdam `base.html` e incluem partials.
- Partials (`_acordos_table.html`, `_mandados_table.html`) contêm a tabela completa:
  - Filtros por coluna (modal com checkboxes, tipo Excel).
  - Ordenação por coluna.
  - Barra de totais/somatórios (valores monetários).
  - Modal de criação/edição com formulário completo.
  - Botão de exclusão com confirmação.
  - Colorização de linhas por status/local/conta.
  - Exportação implícita (dados visíveis na tabela).

### Bibliotecas Frontend (CDN)

- TailwindCSS (`cdn.tailwindcss.com`)
- Feather Icons (`unpkg.com/feather-icons`)
- Chart.js + chartjs-plugin-datalabels (dashboard)
- Google Fonts: Inter

### Dashboard

- KPIs: total, pagos, sem pagamento, ativos, finalizados (para acordos e mandados).
- Gráficos: pagamentos por mês, por UF, por réu, por status.
- Filtros multi-select estilo Excel (status, UF, réu) com dropdown customizado.
- Tabs para alternar entre Acordos e Mandados.
- Visual dark glass (gradiente escuro com glassmorphism).

## Docker e Deploy

### Dockerfile

```dockerfile
FROM python:3.12-slim
# Instala build-essential, curl, ca-certificates
# WORKDIR /app
# COPY requirements.txt → pip install
# COPY . .
# EXPOSE 5001
```

### docker-compose.yml

- Serviço `web` (container: `site-financeiro-web`):
  - `gunicorn -w 3 -k gthread --threads 8 --timeout 120 --bind 0.0.0.0:5001 app:app`
  - Volumes: `./templates:/app/templates:ro`, `./static:/app/static:ro`
  - Redes: `financeiro_net` (bridge), `n8n_net` (external, para integração com n8n)
  - Env file: `.env`
  - Restart: `unless-stopped`

### Caddyfile

```
financeiro.n8n-draconsumidor.com.br {
    encode gzip
    reverse_proxy site-financeiro-web:5001
}
```

### Comandos de Deploy (no servidor Linux)

```bash
# Subir/reconstruir
docker compose up -d --build

# Ver logs
docker logs -f site-financeiro-web

# Reiniciar
docker compose restart web

# Parar
docker compose down
```

## Pontos de Atenção

1. **Case-sensitivity**: Linux diferencia `Images` vs `images`. Há um fix no app.py para `/static/images/logo.png`.
2. **credentials.json**: Contém chave privada da Service Account Google. **NUNCA versionar**.
3. **Sync destrutivo**: Os scripts de sync deletam TODOS os registros antes de reinserir. Alterações feitas diretamente no app são perdidas na próxima sync.
4. **Limites de Supabase**: Queries limitadas a 5000 registros (limit nas consultas).
5. **Templates monolíticos**: Os partials `_acordos_table.html` e `_mandados_table.html` são arquivos grandes com CSS + HTML + JavaScript inline.
6. **Rede n8n**: O docker-compose referencia a rede externa `n8n-docker-caddy_n8n_net` — ela deve existir no servidor.
